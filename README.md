# RadarSmith

Forge and maintain your own technology radars. RadarSmith is a private, self-hosted web app
where the database — not a spreadsheet or a prepared file — is the source of truth for a
radar and its blips: open a radar, edit it in the browser, and see the result immediately.

> [!WARNING]
> RadarSmith is single-tenant with **no accounts, permissions, or authentication**. It is
> meant to be run privately (e.g. behind a VPN or on localhost) for one trusted author, not
> exposed directly to the public internet.

## Features

- **Radar library** — list, create, rename, and delete radars from the browser.
- **Live linked workspace** — an SVG radar and an authoritative blip table stay in sync;
  selecting a marker highlights its row and vice versa.
- **View and Edit modes** — browse a radar read-only with quadrant drill-down, or switch to
  Edit to add, reposition, and delete blips.
- **Accessible by design** — WAI-ARIA graphics roles on the SVG, keyboard-operable markers,
  accessible forms/dialogs, and safe link rendering in descriptions.
- **One-container deploy** — a single Docker image serves the built frontend and the API
  together, backed by PostgreSQL.

## Quick start

Just want to run RadarSmith, not develop it? With Docker and Docker Compose installed:

```bash
make prod-up     # builds the image, runs migrations, starts the app + PostgreSQL
```

This prints the URL once the stack is healthy (http://127.0.0.1:8080). See
[Production deployment](#production-deployment) below for upgrades, backups, and
troubleshooting. Contributors should use [Getting started](#getting-started) instead, which
runs the API and frontend dev servers with hot reload.

## Requirements

- Python 3.13 and [Poetry](https://python-poetry.org/)
- Node.js 24 and npm (for the frontend)
- Docker and Docker Compose (for PostgreSQL, and for the production stack)

## Getting started

```bash
make setup       # install backend and frontend dependencies
make db-up       # start PostgreSQL in Docker
make up-schema   # apply migrations (also seeds a starter radar)
make dev         # run the API on http://localhost:8000/docs
```

In another terminal:

```bash
make fe-dev      # run the frontend on http://localhost:5173
```

The frontend dev server proxies `/api/v1` to the backend on port 8000; the API health check
is served at `GET /api/v1/health`.

### Writing a migration

After changing a SQLAlchemy model, generate and apply a migration from `backend/`:

```bash
cd backend
poetry run alembic -c alembic/alembic.ini revision -m "<describe the change>" --autogenerate
```

Review the generated file in `backend/alembic/versions/` — autogenerate doesn't always infer
the change correctly, and Ruff may flag style issues worth fixing by hand. Then apply and
sanity-check both directions:

```bash
make up-schema    # apply the new migration
make down-schema  # roll it back to confirm downgrade works
make up-schema    # re-apply
```

### Frontend API types

The frontend never hand-writes backend DTOs: `frontend/src/api/schema.d.ts` is generated by
`openapi-typescript` from `backend/openapi.json` and committed to the repo, so `make fe-build`
succeeds without a running backend. After changing any endpoint or schema, regenerate it with:

```bash
make generate-api-types
```

CI runs the same command and fails the build on an uncommitted diff (see
[.github/workflows/ci.yml](.github/workflows/ci.yml)):

```bash
make generate-api-types
git diff --exit-code backend/openapi.json frontend/src/api/schema.d.ts
```

| Command | Purpose |
| --- | --- |
| `make export-openapi` | Export the OpenAPI document to `backend/openapi.json` (deterministic) |
| `make fe-generate-types` | Regenerate the committed frontend API types from `backend/openapi.json` |
| `make generate-api-types` | Export the OpenAPI document, then regenerate the frontend types from it |

## Production deployment

The production image (`Dockerfile`, repo root) builds the frontend and installs production-only
Python dependencies in separate stages, then serves the built frontend and the API from one
non-root container on one port, with a container health check. `deploy/docker-compose.yml` runs
that image alongside PostgreSQL, running migrations as a one-shot job before the app starts.
Everything binds to `127.0.0.1`; there is no TLS or reverse proxy in the MVP.

Start a clean, healthy stack (builds the image, runs migrations, then starts the app):

```bash
make prod-up
```

On first run this also creates `deploy/.env` from `deploy/.env.template` with a randomly
generated PostgreSQL password (see `deploy/init-env.sh`); later runs leave an existing
`deploy/.env` untouched, so manual edits are preserved. PostgreSQL only applies
`POSTGRES_PASSWORD` the first time it initializes its data volume: if you delete `deploy/.env`
to regenerate the password after the named volume already exists, the database's actual role
password will not change and the app will fail to authenticate. Reset the volume (`docker
compose -f deploy/docker-compose.yml down -v`) or edit the password with `ALTER ROLE` instead.

The app is then reachable at http://127.0.0.1:8080 (UI and `/api/v1/*` under one origin).
`docker compose -f deploy/docker-compose.yml ps` shows container health; `make prod-down` sends
`SIGTERM` and stops the stack while keeping the named PostgreSQL volume, so restarting with
`make prod-up` retains prior edits.

### Upgrading

1. Back up the database first (see below).
2. `git pull` (or check out the new release tag).
3. `make prod-up` — rebuilds the image, re-runs the one-shot `migrate` service (harmless if
   there is nothing new to migrate), then restarts `app`. The named PostgreSQL volume and
   `deploy/.env` are untouched.
4. Confirm both containers are healthy: `docker compose -f deploy/docker-compose.yml ps`.

### Backup and restore

Back up or restore the database through the running `db` container:

```bash
# Backup
docker compose -f deploy/docker-compose.yml exec db pg_dump -U radarsmith radarsmith > backup.sql

# Restore (into an empty database)
docker compose -f deploy/docker-compose.yml exec -T db psql -U radarsmith radarsmith < backup.sql
```

### Troubleshooting

- **`docker ... error listing credentials ...` / `docker-credential-... not found`** — a
  broken or missing Docker credential helper. Every `make` target already sets `DOCKER_CONFIG`
  to the repo-committed, empty `.docker-config` directory (see [Makefile](Makefile)), which
  avoids this; if you invoke `docker`/`docker compose` directly instead of through `make`,
  export the same variable yourself (`export DOCKER_CONFIG=$PWD/.docker-config`).
- **Port already in use (`55432`, `8080`, or `5173`)** — another process or project is bound to
  that port. Stop it, or edit the host-side port mapping in
  [dev/docker-compose.yml](dev/docker-compose.yml) or
  [deploy/docker-compose.yml](deploy/docker-compose.yml).
- **App fails to authenticate to PostgreSQL after editing `deploy/.env`** — PostgreSQL only
  applies `POSTGRES_PASSWORD` the first time it initializes its data volume; see
  [Upgrading](#upgrading) above for the fix (reset the volume or `ALTER ROLE`).
- **A container never becomes healthy** — check
  `docker compose -f deploy/docker-compose.yml ps` for status and
  `docker compose -f deploy/docker-compose.yml logs <service>` for details.
- **`make fe-build` or CI's OpenAPI check fails with a diff in `schema.d.ts`** — the committed
  frontend types are stale relative to the backend. Run `make generate-api-types` and commit
  the result.
- **`make test` can't reach the database** — the backend test suite needs a running local
  PostgreSQL; run `make db-up` first.

## Configuration

Backend settings load from `backend/settings.env` (see
[backend/settings.env.template](backend/settings.env.template)). Variables use the
`rs_api_` prefix, e.g. `rs_api_db_url`.

## Supported versions

- **PostgreSQL 18** — pinned in [dev/docker-compose.yml](dev/docker-compose.yml),
  [deploy/docker-compose.yml](deploy/docker-compose.yml), and CI. Other 1x versions likely
  work but are untested.
- **Browsers** — the latest stable release of Chrome, Firefox, Safari, and Edge (desktop and
  mobile). The frontend targets ES2022 with no polyfills and isn't tested against older or
  non-evergreen browsers.

## Continuous integration

Every pull request and push to `main` runs backend lint/typecheck/tests, frontend
lint/typecheck/tests/build, a migration upgrade/downgrade check, an OpenAPI-types-freshness
check, and a production image build, all defined in
[.github/workflows/ci.yml](.github/workflows/ci.yml). Each check is a separate job that fails
independently with its own logs, needs no repository secret, and mirrors a `make` command you
can run locally (see the tables above and [Frontend API types](#frontend-api-types)).

## Releasing

Tag a release only once CI is green on `main` **and** a manual run-through of the
[MVP acceptance boundary](doc/architecture/product-spec.md#mvp-acceptance-boundary) still
holds against a fresh stack. Then:

```bash
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

Keep the tag in sync with the `version` field in [pyproject.toml](pyproject.toml).
